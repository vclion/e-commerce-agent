# 对话连接修复与验收

日期：2026-10-18。用户在工作台发送“帮我生成文案”后收到“Dify 流未正常结束”。

## 原因与处理

本机 Windows 网络可以访问 DeepSeek，WSL 与 Docker 中的直接请求超时；DNS 返回了本机代理的 `198.18.*` 地址。Windows 的既有 HTTP 代理监听 `127.0.0.1:7890`，Linux 不能直接访问这个 Windows 回环端口。

新增可选的 `scripts/windows_proxy.py`，在 Linux 本地 Docker 网桥上监听 `18790`，通过 WSL Windows 互操作的标准输入/输出管道，连接 Windows 既有本地代理。HTTP CONNECT 中的 TLS 数据保持透传；转发器不解析、保存或打印模型请求、回复和密钥。没有更改系统代理、DNS、证书或防火墙设置。

本机私有配置位于被 Git 忽略的 `.runtime/windows-proxy.json`：

```json
{"enabled": true, "listen_port": 18790, "windows_proxy_port": 7890}
```

`scripts/prepare_dify.py` 在启用该配置时，把项目代理写入本地 Dify Compose 覆盖文件的 `plugin_daemon` 环境，内部服务地址继续通过 `NO_PROXY` 直连。`scripts/start.py` 和 Dify 配置脚本会按需拉起转发器，现有数据库、模型配置和应用 Key 保留。未配置该私有文件的环境继续使用原来的网络路径。

转发器依赖 Windows 本地代理仍在运行。更换本机代理端口时，需要相应更新私有配置并重启项目转发器。停用时将 `enabled` 设为 `false`，重新运行 Dify 配置脚本并重新创建 `plugin_daemon`，即可恢复其原始出站配置。

## 对话链路修正

- 后端识别 Dify `workflow_finished` 的失败状态和错误事件，区分网络超时、认证失败和限流，不向页面透出插件堆栈或凭据。
- 上游已报失败时，即便此前出现过 `message_end`，本地运行记录仍标记失败；缺少完成事件和空回复不能标记成功。
- 前端校验流是否收到完成事件，支持 CRLF 和末尾未带空行的帧；意外断流保留已收到的正文。
- 失败回复提供“重试这条消息”，重新加载历史后仍可使用；重试由用户点击触发，不自动重复业务写入。
