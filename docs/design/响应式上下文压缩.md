# 响应式上下文压缩兜底

更新：2026-10-22。正常请求仍采用最近 3 轮完整原文、简短任务线索和少量活跃索引；不因为启用兜底而每轮增加模型调用。

## 触发顺序

1. 可选索引、长期补充先受各自小预算和总额度控制，放不下时不装载。
2. 最近原文本身放不下时，临时压缩其中较早的轮次，保留最新一轮完整原文和用户本轮原问题。
3. 如果模型明确返回上下文过长，且尚未输出回答、尚未调用任何工具，则最多自动重试一次。重试先去除可选历史补充，并按较小目标预算决定是否压缩较早轮次。
4. 最新原文及保护信息仍装不下、整理服务失败或摘要仍过长时，明确失败，不反复递归压缩或静默截断。

正常默认 3 轮，因此压缩对象为最早 2 轮；配置其他近期轮数时，仍保留最后一轮原文。每个阶段最多调用一次整理模型，同一请求最多为“预检一次 + 上游超限后一次”，均从原文重新生成，不摘要套摘要。整理输入本身也有额度限制。

## 保护内容

- 被压缩轮次的用户原话完整保留，避免丢失约束、决定、目标和用户给出的数字。
- 轮次、来源 ID、运行状态、实际操作结果保持原样。
- 助手原文中的常见数字、单位和资源标识额外提取保留，并标为未核实的字面值，不据此认定业务状态。
- 最新一轮问答及本轮问题不改写。细节不足时仍可 history_read 原文回查。

摘要仅写入本轮短期快照，不覆盖 ChatRun、分段、索引或长期记忆；沿用快照过期清理及遗忘依赖检查。普通的聊天完成后台抽取仍按原设置工作，压缩器本身不保存记忆。

## 自动重试边界

只识别明确的上下文超限错误，包括受支持的 HTTP 错误正文和 Dify error / workflow_finished 事件。认证失败、限流、超时、一般插件失败不触发压缩重试。

开始重建前，后端锁定旧工具凭证并检查本轮工具尝试记录。任何工具尝试，包括读取，都阻止自动重试；出现工具调用事件或回答片段也不重试。旧凭证先废止，新尝试使用新凭证和新的 Dify 上游会话，本地 session_id 与 run_id 保持一致。工具入口在取得凭证锁后再次验证，阻止迟到旧调用。

重建后重新检查来源、权限、epoch 及运行状态。遗忘、撤权或运行中断后，旧摘要不能重新激活。已完成的业务操作仍通过原有审计回执保留，绝不因压缩而重放。

重试目标优先采用原快照大小的 60%，但会为最新原文、保护信息、最小摘要留空间。目标不是硬性压到 60%；无法获得比原快照更小的安全输入时停止重试。
